# Cleopatra AI — Security Model

**Status:** Proposal / Phase 0 audit output. Nothing described here is implemented.

---

## 1. Threat framing

An LLM-driven agent with tool access to a business system introduces exactly one new class of risk this project hasn't had before: **the caller issuing a request is, from the API's point of view, indistinguishable from a normal authenticated user — but the actual instruction executing a tool call was generated by a model that can misread intent, misremember a fact, or be manipulated by adversarial text it reads along the way** (e.g. a customer's own free-text order notes containing something that looks like an instruction). Every control below exists to make sure that even in the worst case — the model is confidently wrong, or actively confused by injected text — the *system* still behaves exactly as if a human had to approve each consequential step, because a human does.

## 2. Identity & Permission Enforcement

**The AI never has its own identity or its own permission set.** Every request to `POST /api/ai/chat` carries the calling staff member's own JWT, through the exact same `requireAuth` middleware every other route uses. The orchestrator receives `req.auth` — already resolved (permissions, `accessibleBranchIds`, role names) by existing middleware, not recomputed.

```
User can view treasury       → AI can call get_treasury_summary for them.
User cannot view treasury    → the tool dispatcher rejects the call before
                                execute() runs; Claude receives a tool_result
                                explaining *why* (missing permission X), not a
                                silent empty result and not a raw 403.
```

**Enforcement point:** the tool dispatcher, not each tool's own body. Every tool declares its `requiredPermission` (see `CLEOPATRA_AI_TOOLS.md`); the dispatcher calls `hasPermission(ctx.auth.permissions, tool.requiredPermission)` — the identical function `requirePermission()` middleware already uses — **before** invoking `tool.execute()`. This means a bug inside a tool's own implementation can never accidentally skip the permission check; it's structurally impossible to reach `execute()` without having passed it, the same guarantee route-level middleware gives every existing controller.

**Branch scoping** follows the same pattern already fixed for Treasury (تكملة 62) and the financial dashboard widget (تكملة 69): `ctx.accessibleBranchIds` is threaded into every tool that reads/writes branch-scoped data, and `'all'` is only ever passed when `ctx.auth.roleNames.includes('SUPER_ADMIN')` — identical to `accessibleBranchScope(auth)`'s existing behavior. A tool must never accept a caller-supplied `branchId` and trust it blindly (the exact bug class تكملة 62 fixed) — it always intersects against `ctx.accessibleBranchIds` server-side.

**Sensitive-data carve-outs** (payroll, cost prices) keep their existing, stricter gates verbatim — `get_employee_payroll` hard-checks `SUPER_ADMIN`, not a normal permission string, exactly like `EmployeeProfilePage.tsx` does today. The AI layer does not get to be more permissive than the UI it's standing in for.

## 3. Business-Rule Boundary

Rule 3/4 ("never change Pricing Logic / الدفاتر/الورق/التراج/الهالك calculations without explicit approval") applies to Cleopatra AI exactly as it applies to any other feature request — with one added guarantee specific to an LLM layer: **the model cannot compute a price itself.** `calculate_price` (`CLEOPATRA_AI_TOOLS.md`) is a tool call into the real pricing engine; there is no path by which Claude's own arithmetic ever reaches a customer-facing number. If the model states a price in prose without having called the tool first, that is a hallucination to be caught by §6, not a legitimate answer path — the system prompt instructs this explicitly (`CLEOPATRA_AI_ARCHITECTURE.md` §4), and it is testable: any priced answer without a preceding `calculate_price` tool call in the same turn is a defect.

## 4. Confirmation Architecture

**Every WRITE tool call returns a confirmation payload instead of executing, the first time Claude proposes it.** The user (a human, in the chat UI) must explicitly approve before the actual service function runs.

```json
{
  "requiresConfirmation": true,
  "action": "create_treasury_entry",
  "summary": "تسجيل حركة خزينة: مصروف 500 ج.م — إيجار سبتمبر، فرع كليوباترا",
  "impact": "هيقلل رصيد خزينة فرع كليوباترا بـ500.00 ج.م. مينفعش يتراجع عنه إلا بحركة تصحيح يدوية.",
  "toolName": "create_treasury_entry",
  "toolInput": { "branchId": "...", "type": "EXPENSE", "amount": 500, "category": "إيجار" },
  "confirmationToken": "<signed, short-lived token — see below>"
}
```

**`confirmationToken` design:** a signed (HMAC, using a server-side secret already available via the existing env-var pattern — no new secret-management mechanism needed), short-TTL (e.g. 5 minutes) token whose payload is `{ userId, toolName, toolInput, issuedAt }`. This is deliberately **stateless** — no new database table or in-memory pending-actions store is required, which matters concretely on Render's Starter plan (a single instance today, but a signed token survives an instance restart or, later, multiple instances; an in-memory map would not). When the user clicks "confirm" in the chat UI, the frontend re-submits the token to a small, dedicated endpoint (e.g. `POST /api/ai/confirm`); the backend verifies the signature, verifies it hasn't expired, verifies the **re-supplied `userId` still matches the current session** (a token cannot be confirmed by anyone other than the user it was issued to), and only then calls the real tool's `execute()`.

**Which tools require confirmation:** every tool classified `WRITE` in `CLEOPATRA_AI_TOOLS.md`, with no exceptions in v1. The request's own examples (delete, financial transactions, price changes, closing treasury day, settings changes, destructive operations, bulk modifications) are exactly the shape already reflected in that catalog's risk tiers. A future refinement *could* let low-risk WRITE tools (e.g. `create_lead`) skip confirmation once the system has a track record — that is an explicit, later, opt-in decision per tool, never a default.

**Copy for the `summary`/`impact` fields must be Arabic, plain language, and name the real numbers/entities involved** — never "an action will be performed." This is a UX requirement, not just a security one: the confirmation is only meaningful if a human reading it in two seconds actually understands what they're approving.

## 5. Auditability

**Reuses the existing `AuditLog` model and `recordAudit()` function — no new audit mechanism.** Every executed WRITE tool call — after confirmation, at the moment `execute()` actually runs — calls `recordAudit()` exactly as the equivalent existing controller already does for a human-initiated version of the same action (e.g. `create_treasury_entry` calls `recordAudit()` with `entityType: 'TreasuryEntry'`, `action: 'CREATE'`, the same shape `treasuryEntries` controller already writes).

**What's new, and does need one small additive field:** there is currently no way to tell, from an `AuditLog` row alone, whether an action was taken by a human directly or by Cleopatra AI on that human's behalf. `previousValue`/`newValue` are both `Json?` already, so the *minimum-risk* option requires zero migration — embed provenance inside the existing JSON payload:

```json
// newValue, as already written by createManualTreasuryEntry — with one added key:
{ "amount": 500, "category": "إيجار", "branchId": "...", "_source": "cleopatra_ai", "_userMessage": "سجل مصروف إيجار سبتمبر ٥٠٠ جنيه" }
```

This is workable for v1 and requires no schema change (consistent with "Do NOT modify database schema... in this phase," and keeps the option open for Phase 2 without pre-committing to a migration now). **If the volume of AI-initiated actions grows enough that filtering/reporting on them becomes a real, recurring need**, the cleaner long-term design is one new nullable column, e.g. `AuditLog.initiatedByAgent String?` (`"cleopatra_ai"` or null) — small, additive, backward-compatible, and explicitly flagged in `CLEOPATRA_AI_IMPLEMENTATION_PLAN.md` as a migration requiring the owner's explicit approval before being added, per rule 10.

**Also recorded, per confirmed action:** the tool name, the exact input the model proposed, the user's own natural-language request that led to it, the confirmation token's issuance/confirmation timestamps, and the result. This is strictly more traceable than a manually-clicked UI action already is today, not less.

## 6. Failure Handling

| Situation | Behavior |
|---|---|
| **Unknown request** (nothing in the tool catalog answers it) | Claude says so directly — the system prompt instructs "if no tool can answer this, say you don't have a way to check that, don't guess." Never silently invent an answer. |
| **Missing information** (e.g. "افتح أوردر جديد" with no customer named) | The model asks a clarifying question before calling a tool with incomplete/guessed input — same interactive-question pattern already established and explicitly preferred by the owner for the smart-paste feature (تكملة 79: "حابب إن الحاجات الناقصه يسألني عليها"). |
| **Permission denial** | Tool dispatcher returns a `tool_result` stating which permission is missing, in Arabic, phrased as a fact ("محتاج صلاحية `treasury.view`") — Claude relays this plainly, never pretends the data doesn't exist. |
| **Tool failure** (service throws, e.g. `CampaignNotFoundError`) | Caught by the dispatcher, returned as a `tool_result` with `is_error: true` (per Anthropic tool-use semantics) carrying a safe, non-stack-trace message; Claude explains the failure in plain language rather than the loop crashing. |
| **Database/network failure** | Same as above, generic "تعذر الوصول للبيانات دلوقتي، جرّب تاني" — never a raw error surfaced to the end user, consistent with rule 17 (graceful handling of transient failures). |
| **Invalid arguments** (Claude's tool call fails Zod validation) | Rejected before `execute()` runs; the validation error is returned as a `tool_result` so Claude can retry with corrected input — the model gets one to two retries within a turn, then surfaces the failure to the user rather than looping indefinitely. |
| **Ambiguous commands** ("امسح الطلب" with 3 matching orders) | The model must call a search tool first and ask the user which one, never guess the most-recent or first match. |
| **AI hallucination** (states a number/status without a preceding tool call) | This is a prompt-and-eval problem, not something a runtime check can catch with certainty — mitigated by (a) the explicit system-prompt instruction (§`CLEOPATRA_AI_ARCHITECTURE.md` §4), (b) an eval suite (see Implementation Plan, Phase 1) that specifically tests "does the model call the tool before stating a figure," and (c) every stated fact being checkable against the real system by the human reading it, since nothing here removes the existing UI — Cleopatra AI is an addition, not a replacement for looking something up manually. |
| **Conflicting business rules** (e.g. asked to close a treasury day that's already closed) | The underlying service already raises a typed error for this (`DayAlreadyClosedError`) — the tool surfaces it as-is; Cleopatra AI does not add a second opinion on top of a business rule the service layer already owns. |

**Fail-safe default:** whenever a tool's own permission requirement, branch scope, or business-rule check is ambiguous or the dispatcher cannot resolve it confidently, the default is **refuse and say so**, never "attempt and see." This mirrors rule 11 (no changes to legacy logic without documented impact analysis) applied to runtime decisions, not just code changes.
