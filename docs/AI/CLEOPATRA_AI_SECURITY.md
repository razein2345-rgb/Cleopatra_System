# Cleopatra AI — Security Model

**Status (updated 2026-09-18):** Implemented and verified through Task 15.7. Read-only, local-only, zero write capability. This document describes the system as it actually exists, not a proposal.

---

## 1. Threat framing (unchanged)

An LLM-driven agent with tool access to a business system introduces one risk class this project hasn't had before: the caller issuing a request is, from the API's point of view, indistinguishable from a normal authenticated user — but the actual instruction executing a tool call was generated by a model that can misread intent, misremember a fact, or be manipulated by adversarial text it reads along the way. Every control below exists to make sure the system still behaves correctly even when the model is confidently wrong.

**One risk the original threat model didn't need to consider is now closed by construction rather than by control:** because there are zero write tools, there is no path by which a confused or manipulated model can change a real business record. The confirmation-architecture design in the original proposal (§4 below) exists only as a historical record — it was never built, because nothing currently needs it.

## 2. Identity & Permission Enforcement (as built)

**The AI never has its own identity or its own permission set.** Every request to `POST /api/ai/chat` carries the calling staff member's own JWT through `requireAuth` — the identical middleware every other route uses (`apps/api/src/routes/ai.ts`). The orchestrator receives `req.auth` already resolved by existing middleware, not recomputed.

```
User can view treasury       → the AI can call get_treasury_summary for them.
User cannot view treasury    → dispatchTool() rejects the call before execute()
                                runs; the model receives a tool_result explaining
                                which permission is missing, never a silent empty
                                result and never a raw 403.
```

**Enforcement point:** `dispatchTool()` inside `aiAgentService.ts`, not each tool's own body. Every one of the 24 tools declares its `requiredPermission` (`CLEOPATRA_AI_TOOLS.md`); the dispatcher checks it — the identical function every controller's `requirePermission()` middleware uses — **before** `tool.execute()` is ever called. A bug inside a tool's own implementation cannot skip this check; it is structurally unreachable without passing it first.

**Sensitive-data carve-outs keep their existing, stricter gates verbatim** — `get_employee_payroll` hard-checks `requiresSuperAdmin: true`, exactly like `EmployeeProfilePage.tsx`'s own gate. The AI layer is never more permissive than the UI it stands in for.

**Two deterministic code-level guards go beyond simple permission checking (Task 12):**

- **Guard A** (`readGuardMetadata.ts`) — if a `get_*`/detail tool is called with an id that doesn't look like the entity's real UUID (a human name, a quotation number, an order number), the dispatcher substitutes the paired `search_*` tool automatically, still subject to that search tool's own permission check, rather than letting a malformed lookup either fail confusingly or — worse — silently match the wrong record.
- **Guard B** (`correctionDetection.ts`) — if the user's message contains an explicit correction marker (a small, deliberately narrow, deterministic Egyptian-Arabic pattern set — not general NLP, per Task 11's own finding that broad language understanding isn't warranted here), reuse of the OLD conversation-context entityId in a `get_*` call is rejected before `execute()` runs.

Both guards exist because Task 10's live regression testing proved prompt-only wording is not reliable enough on its own for qwen3 — the guards are a deterministic backstop, not a replacement for the prompt wording (which is still present and still matters).

## 3. Business-Rule Boundary (unchanged, verified)

Rule 3/4 ("never change Pricing Logic / الدفاتر/الورق/التراج/الهالك calculations without explicit approval") applies exactly as it does to any other feature. **The model cannot compute a price itself** — `calculate_price` is a tool call into the real pricing engine (`packages/shared/src/pricing/*` via `pricingEngineService.ts`), the same function the order composer's own live preview calls. There is no code path by which the model's own arithmetic reaches a stated price.

## 4. Confirmation Architecture — proposed, never built, not currently needed

The original proposal described a signed, short-TTL confirmation-token flow for write tools. **This does not exist in the codebase.** It is not needed today because there are zero write tools to confirm. This section is kept only as a historical record of the original design, in case a future, separately-approved write phase ever needs it — it is not an active or scheduled piece of the current system.

## 5. Auditability

Not applicable to the current implementation in the way the original proposal described (audit-logging a write action) — **there are no AI-initiated writes to audit.** Every AI action today is a permission-checked read, and reads are not currently written to `AuditLog` by any part of the system (consistent with how the equivalent human-initiated reads already work — `AuditLog` records mutations, not queries). If write tools are ever added under separate approval, the original design (embedding `_source: 'cleopatra_ai'` provenance in the existing `AuditLog.newValue` JSON, with an optional future `AuditLog.initiatedByAgent` column if volume ever justifies it) remains the reasonable approach — but nothing here is implemented or scheduled.

## 6. Failure Handling (as built, verified against tests)

| Situation | Behavior, as implemented |
|---|---|
| **Unknown request** (nothing in the tool catalog answers it) | The model is instructed via the system prompt to say it has no way to check, rather than guessing. |
| **Missing information** | The model is expected to ask a clarifying question before calling a tool with guessed input; this is prompt-level guidance, not a runtime-enforced control. |
| **Permission denial** | `dispatchTool()` returns a `tool_result` naming the missing permission in Arabic; the model relays this, it does not pretend the data doesn't exist. Covered by dedicated tests in `aiAgentService.test.ts`. |
| **Tool failure** (`execute()` throws) | Task 13/13.1: caught by the dispatcher, logged server-side via `console.error` (this codebase's existing convention), and surfaced to the model as a safe `tool_result` with `isError: true` and a generic message — never a raw stack trace. Verified by a dedicated regression test that asserts both the server-side log call and the client-facing safety in the same scenario. |
| **Database/network failure** | Same generic-fallback path as tool failure — no raw error ever reaches the end user. |
| **Invalid arguments** | Rejected before `execute()` runs; covered by dedicated input-validation tests. |
| **Zero tool calls where exactly one was clearly warranted** (Task 15.5/15.6 — qwen3 sometimes returns no tool call even when routing narrowed to one obvious tool, and Ollama has no way to force one) | Task 15.7's deterministic HELP fallback: if routing narrowed to exactly `search_help_topics` and the model returned zero tool calls, the application itself dispatches that exact call — through the same `dispatchTool()` path, so the same permission/schema/logging behavior applies — and gives the model one more turn to answer from the real result. Fires at most once per request. The model's own discarded, ungrounded text is never shown to the user. |
| **Non-deterministic tool-result discarding** (Task 15.1 — a live 7-run trial found the model discarding a correct tool result in 3/7 runs from sampling variance alone) | Task 15.2: `options.temperature: 0` on every Ollama request — greedy decoding, not sampled. |
| **Bounded iteration** | The orchestrator loop stops after a fixed number of tool-call iterations rather than looping forever; covered by a dedicated test. |

**Fail-safe default (unchanged):** whenever a permission, branch scope, or business-rule check is ambiguous, the default is refuse and say so, never attempt and see.

## 7. Read-only boundary — verified, current

- **AI tools:** 24
- **Write tools:** 0
- **Tool files containing any `.create(`/`.update(`/`.delete(`/`.upsert(` call:** 0 (verified by direct inspection of every file under `apps/api/src/services/ai/tools/`)
- **Migrations added for AI:** 0
- **External LLM providers:** 0 — Ollama only, local-only, no `ANTHROPIC_API_KEY` or equivalent exists anywhere in this codebase's AI path.

This boundary is enforced structurally (no write tool is registered in `AI_TOOLS`, so there is nothing for the dispatcher to execute), not by a runtime toggle that could be silently flipped.
