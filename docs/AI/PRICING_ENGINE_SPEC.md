# برومبت لـ Claude Code: منطق العمل (Business Logic) لنظام مطبعة Cleopatra Press

> **الغرض من هذا الملف**: هذا برومبت كامل يحتوي على كل منطق العمل (Business Logic) اللي اتبني واتأكد منه بالتفصيل مع صاحب المطبعة. المطلوب من Claude Code إنه يستخدم المواصفات دي **حرفيًا** كأساس لبناء نظام ERP، من غير ما يخترع أو "يحسّن" أي معادلة من عنده. أي رقم أو قاعدة مكتوبة هنا **تم تأكيدها فعليًا مع صاحب العمل** عن طريق أمثلة محلولة يدويًا.

## 1) نبذة عن العمل

مطبعة (Cleopatra Press) بتقدم:
- طباعة أوفست: ورق سايب، دفاتر (فواتير/إيصالات مرقمة)، أظرف، فولدرات

## 3) محرك التسعير (الجزء الأهم - نفّذه بالظبط زي ما هو)

### 3.1) جدول "عائلات المقاسات" (Size Families)

كل عائلة عندها "فرخ كامل" وقائمة مقاسات، كل مقاس له **عدد القطع اللي بيطلعها من الفرخ الكامل**:

```js
const FAMILIES = {
  standard:    { base: 'regular', sizes: [['12.5×17.5',32], ['17.5×25',16], ['25×35',8], ['35×50',4], ['50×70',2], ['70×100',1]] },
  foolscap:    { base: 'regular', sizes: [['11.5×16.5',36], ['16.5×23',18], ['23×33',9]] },
  extra1:      { base: 'regular', sizes: [['10×14',50], ['14×20',25], ['20×28',10], ['28×40',5]] },
  extra2:      { base: 'regular', sizes: [['10×15',44], ['15×20',22], ['20×30',11], ['30×40',5]] },
  extra3:      { base: 'regular', sizes: [['11.5×20',30], ['20×23',15], ['20×25',14], ['23×25',12]] },
  gawab:       { base: 'regular', sizes: [['11×14',44], ['14×22',22], ['22×28',10], ['28×42',5]] },
  aSeries:     { base: 'regular', sizes: [['A7',64], ['A6',32], ['A5',16], ['A4',8], ['A3',4], ['A2',2], ['A1',1]] },
  koshiaGayer: { base: 'gayer',   sizes: [['11×16.5',32], ['16.5×22',16], ['22×33',8], ['33×44',4], ['44×66',2], ['66×88',1]] },
};
```

- `base` = "regular" (فرخ عادي 70×100) أو "gayer" (فرخ جاير 66×88) - نوعين مختلفين من الفروخ، لكل واحد أسعار مستقلة تمامًا حتى لو نفس اسم الخامة.
- الرقم جنب كل مقاس = **عدد القطع اللي بتطلع من فرخ كامل واحد بنفس العائلة**.
- هذا الجدول **قابل للتعديل من شاشة إعدادات** (إضافة مقاس جديد لعائلة، أو عائلة جديدة بالكامل) - لازم أي مقاس مستخدم فعليًا في حسابات جارية يكون **محميًا من الحذف**.

### 3.2) نظام "التدرج" (Tiering) - دفاتر وورق سايب فقط

**المشكلة اللي بيحلها**: العميل بيطلب مقاس صغير (مثلاً 10×15)، لكن اقتصاديًا أرخص إننا نطبع على مقاس أكبر (فيه نسخ متكررة منه) لو الكمية كبيرة، بدل ما نستهلك فرخ كامل لكل نسخة صغيرة.

```js
const GROUPS = {
  g1: { family: 'extra2',   below: '20×30', above: '30×40' },
  g2: { family: 'standard', below: '25×35', above: '35×50' },
  g3: { family: 'extra1',   below: '20×28', above: '28×40' },
  g4: { family: 'gawab',    below: '22×28', above: '28×42' },
  g5: { family: 'foolscap', below: '23×33', above: '23×33' }, // مقاس واحد ثابت، مفيش تدرج فعلي
  gA: { family: 'aSeries',  special: 'A' },                    // قاعدة خاصة (تحت)
};
```

**قاعدة الاختيار العامة** (لأي جروب عادي مش special):
```
calcLabel = (below === above) ? below : (qty >= threshold ? above : below)
```
- `threshold` = حد قابل للتعديل من الإعدادات:
  - **حد الدفاتر** (`notebookThreshold`) الافتراضي = **30**
  - **حد الورق السايب** (`looseThreshold`) الافتراضي = **3000**

**قاعدة خاصة لمقاسات A** (الجروب `gA`):
```
إذا كان المقاس الحقيقي = A4:
    calcLabel = (qty > 10) ? 'A3' : 'A4'      // ملحوظة: حد A4 التحديد هو 10 وليس نفس عتبة الجروب العادية
غير كده (يعني A5/A6/A7):
    calcLabel = (qty >= threshold) ? 'A3' : 'A4'
```

**معامل التكرار** (كام قطعة من المقاس الحقيقي تدخل في مقاس الحساب):
```
repeat = round( area(calcLabel) / area(realLabel) )
```
حيث `area("W×H") = W * H` (حساب مساحة بالضرب المباشر). هذا الحساب **مؤكد** بمثال محلول (10×15 داخل 20×30 = 4 نسخ، داخل 30×40 = 8 نسخة).

**عدد الأفرخ الكاملة المطلوبة**:
```
units = totalUnits / repeat
sheetsNeeded = ceil( units / calcCount ) + wasteSheetsDefault
```
حيث `calcCount` = عدد قطع مقاس الحساب (calcLabel) داخل الفرخ الكامل (من جدول FAMILIES).

**⚠️ التقريب دائمًا لأعلى (Ceiling) في كل مكان** - مفيش تقريب لأقرب رقم، دايمًا لفوق.

### 3.3) نظام الترقيم المستقل (Numbering) - **مهم جدًا، منفصل تمامًا عن حساب الطباعة**

**السبب**: ماكينة الترقيم أقصى مقاس تقدر تستوعبه هو **33×23 سم**. فمقاس الطباعة (اللي ممكن يبقى كبير زي 30×40) مش هو نفسه مقاس الترقيم.

```js
const NUMBERING_RULES = {
  g1: { targetLabel: '20×30' },
  g3: { targetLabel: '20×28' },
  g4: { targetLabel: '22×28' },
  g5: { targetLabel: '23×33', fixed: true },
  gA: { targetLabel: 'A4', special: 'A' },
};
// استثناء خاص للجروب g2 (بدون مضاعفة، تحويل مباشر لكل مقاس):
const NUMBERING_GROUP2_MAP = { '12.5×17.5':'17.5×25', '17.5×25':'17.5×25', '25×35':'25×35' };
```

**القاعدة الأهم (اتأكدت بعد تجربة فعلية وتصحيح غلطة سابقة)**:
> **الترقيم بياخد نفس معامل تكرار المقاس المستهدف بس - من غير أي مضاعفة (×2) حتى لو فرخ الطباعة كان كبير.**
> (كان فيه محاولة سابقة لمضاعفة عدد تراجات الترقيم لو فرخ الطباعة كبير، لكن ده غلط وتم إلغاؤه بعد اختبار حقيقي - **لا تضف مضاعفة هنا إطلاقًا**.)

```
repeat = round( area(targetLabel) / area(realLabel) )   // لمقاسات A: نسبة العدد مباشرة من الجدول
numberingUnits = totalUnits / repeat
numberingRuns = ceil( numberingUnits / 1000 )
numberingCost = numberingRuns * numberingRunPrice
```

**حساب "نهاية الترقيم" (رقم آخر إيصال/دفتر) - منفصل تمامًا عن حساب تكلفة التراجات:**
- **ورق سايب**: `numEnd = startNumber + qty - 1` (كل ورقة رقم مستقل)
- **دفاتر**:
  - لو "أصل فقط": كل دفتر فيه **100 صفحة مرقمة منفردة** → `numEnd = startNumber + (qty * 100) - 1`
  - لو "أصل + نسخ" (كربون): كل دفتر فيه **50 "طقم" فقط** (الأصل والصورة ياخدوا نفس الرقم عن طريق الكربون، بغض النظر عن عدد النسخ) → `numEnd = startNumber + (qty * 50) - 1`

### 3.4) حساب "ورق سايب" (Loose Paper)

المدخلات: نوع الفرخ (عادي/جاير)، نوع الورق، المقاس، الكمية، عدد الألوان، لون الحبر (نص وصفي فقط)، **وجه واحد/وجهين**، هل تصميم، هل ترقيم، أفرخ تهدير إضافية.

```
لو الفرخ "جاير":
    repeat = عدد قطع المقاس مباشرة من عائلة koshiaGayer (بدون أي تدرج)
    sheetsNeeded = ceil(qty / repeat) + waste
لو الفرخ "عادي" (فيه تدرج):
    calc = resolveTieredCalc(...)
    units = qty / calc.repeat
    sheetsNeeded = ceil(units / calc.calcCount) + waste

paperCost = sheetsNeeded * سعر الفرخ
zincCost  = zincPrice(75 افتراضي) * عدد الألوان
printUnits = (لو فيه تدرج) qty/calc.repeat وإلا qty
printRuns  = ceil(printUnits / 1000) * عدد الألوان * عدد الأوجه (1 أو 2)   // ⚠️ "وجهين" يضاعف عدد التراجات فقط
printCost  = printRuns * printRunPrice(75 افتراضي)
numberingCost = (لو مفعّل) حسب نظام الترقيم أعلاه
designCost = (لو "تصميم جديد") designPrice(75 افتراضي) وإلا صفر

subtotal = paperCost + zincCost + printCost + numberingCost + designCost
total = subtotal * (1 + profitPercent/100)     // profitPercent الافتراضي 25%
```

### 3.5) حساب "الدفاتر" (Notebooks) - أهم قسم في النظام

المدخلات: عدد الدفاتر، نوع المحتوى (أصل فقط / أصل + عدد نسخ)، عدد الألوان، المقاس الحقيقي، نوع الورق، تصميم، ترقيم (مع رقم البداية)، سعر تقفيل الدفتر الواحد، نوع التجليد (نص وصفي)، لون الحبر (نص وصفي)، أفرخ تهدير.

```
sheetsPerNotebook = (نوع=أصل فقط) ? 100 : (50 + 50 * عدد النسخ)
totalSheetsFlat = qty * sheetsPerNotebook

calc = resolveTieredCalc(realSize, qty, notebookThreshold)   // نفس نظام التدرج أعلاه
units = totalSheetsFlat / calc.repeat

printRuns = ceil(units / 1000) * عدد الألوان
printCost = printRuns * printRunPrice

// الترقيم منفصل تمامًا (نظام الترقيم المستقل أعلاه) - بياخد نفس totalSheetsFlat لكن بمعامل تكرار مختلف
numberingCost = ...  (زي 3.3 فوق)

sheetsNeeded = ceil(units / calc.calcCount) + waste
paperCost = sheetsNeeded * سعر الفرخ
zincCost = zincPrice * عدد الألوان
designCost = (تصميم جديد) ? designPrice : 0
bindingCost = سعر_تقفيل_الدفتر_الواحد * qty

subtotal = designCost + zincCost + printCost + numberingCost + paperCost + bindingCost
total = subtotal * (1 + profitPercent/100)
```

**مثال محلول مؤكد** (استخدمه كـ Unit Test):
> 100 دفتر، أصل + 3 صور، مقاس 10×15، مرقم يبدأ من رقم 1
> - totalSheetsFlat = 100 × (50+150) = 20,000
> - الجروب g1، الكمية 100 ≥ عتبة 30 → مقاس الطباعة = 30×40، معامل التكرار 8
> - وحدات الطباعة = 20,000 / 8 = 2,500 → تراجات الطباعة = ceil(2500/1000) = 3
> - الترقيم: الهدف 20×30، معامل التكرار 4 (بدون مضاعفة!) → وحدات الترقيم = 20,000/4 = 5,000 → **تراجات الترقيم = 5** ✅ (هذا الرقم اتأكد فعليًا وصُحح بعد غلطة سابقة)
> - نهاية الترقيم = 1 + (100 × 50) - 1 = **500** (لأنه "أصل+نسخ" فبيتحسب 50 مش 100)

### 3.6) حساب "الأظرف" (Envelopes) - **لا يوجد تدرج مقاسات هنا إطلاقًا**

```
design = (تصميم جديد) ? envelopeDesignPrice(100 افتراضي) : 0
zinc = envelopeZincPrice(75 افتراضي) * عدد الألوان
runs = ceil(qty / 1000) * عدد الألوان
printCost = runs * envelopePrintRunPrice(100 افتراضي)
envelopesCost = qty * سعر_الظرف_الجاهز_للقطعة   // بيتكتب يدويًا حسب سعر المورد وقتها

subtotal = design + zinc + printCost + envelopesCost
total = subtotal * (1 + profitPercent/100)
```

### 3.7) حساب "الفولدرات" (Folders)

نفس منطق ورق سايب في حساب عدد الأفرخ (تدرج على الفرخ العادي أو مباشر على الجاير)، بالإضافة إلى:

```
sello = (سلوفان مفعّل) ? sheetsNeeded * sellophanePricePerSheet(4 افتراضي) : 0
riza, jarab (جراب داخلي), forma (فورمة), taksir (تكسير وتلزيق) = أسعار تُكتب يدويًا لكل بند (اختيارية، صفر لو فاضية)

subtotal = designCost + zincCost + printCost + paperCost + riza + jarab + forma + taksir + sello
total = subtotal * (1 + profitPercent/100)
```

### 3.8) حساب "اللوحات والإعلانات" (Boards & Signage) - **مستقل بالكامل، بالمتر مش بالفرخ**

الخامات: بنر (بدون/مع تصميم)، فينيل عادي (بدون/مع سلوفان)، فينيل برنت اند كت (بدون/مع سلوفان)، فلكس، سيسرو.

**الحالة العادية** (بنر/فينيل عادي/فلكس/سيسرو):
```
pieceArea (م²) = (العرض بالسم /100) * (الارتفاع بالسم /100)
totalArea = pieceArea * الكمية
total = totalArea * سعر_المتر_حسب_الخامة_والخيارات
```

**حالة "فنيل برنت اند كت"** (مختلفة تمامًا - عدد القطع اللي بتطلع من المتر المربع):
```
gapCM = المسافة_بين_القطع_مم (افتراضي 5مم) / 10
perRow = floor( (100 + gapCM) / (عرض_القطعة_سم + gapCM) )
perCol = floor( (100 + gapCM) / (ارتفاع_القطعة_سم + gapCM) )
piecesPerMeter = perRow * perCol
metersNeeded = ceil( qty / piecesPerMeter )
total = metersNeeded * سعر_المتر
```
**⚠️ قسم اللوحات لا يُضاف عليه profitPercent% - السعر النهائي هنا هو التكلفة مباشرة (سعر المتر أصلاً شامل الربح من الإعدادات).**

### 3.9) منتجات جاهزة / خدمات

total = سعر_الوحدة * الكمية   // بدون أي نسبة ربح إضافية (السعر مُدخل جاهز في الإعدادات)

## 4) منطق الفاتورة والتحصيل (Invoice & Collection)

- **نسبة الربح (profitPercent)**: قيمة ثابتة عامة من الإعدادات (افتراضي 25%)، **مطبقة بالفعل داخل كل معادلة تسعير فوق** (subtotal → total)، وهي القيمة الافتراضية لأي بند جديد.
  > **تعديل (owner, 2026-08-10)**: يُسمح الآن بتعديل نسبة الربح **لكل بند على حدة** (`profitPercentOverride`) بدل ما تكون read-only بالكامل زي ما كان مكتوب هنا أصلاً — قرار صريح من صاحب المشروع بعد ما اتعرض عليه التعارض مع النص الأصلي. لو مفيش override، البند يستخدم `Setting.profitPercent` العام زي ما هو موضح فوق. الرقم المعروض "مبلغ الربح" = مجموع (`item.total - item.subtotal`) لكل البنود، بنفس القيمة الفعلية المستخدمة (override أو العام).
- **تعديل يدوي لتكلفة الزنك/التراج المحسوبة (owner, 2026-08-10)**: البنود من نوع ورق سايب/دفاتر/أظرف/فولدرات فيها مفتاح "محسوب" — لما يكون شغّال (الافتراضي)، `zincCost`/`printCost` بيتحسبوا زي المعادلات فوق بالظبط. لما يتقفل، الموظف يقدر يكتب رقم يدوي بدل الاتنين (`zincCostOverride`/`printCostOverride`) وده اللي بيتجمع في الـ`subtotal` بدل الرقم المحسوب. باقي المعادلة (paperCost/numberingCost/designCost والربح) فاضلة زي ما هي دايمًا محسوبة من السيرفر — مفيش تعديل يدوي عليها. **قرار صريح من صاحب المشروع** رغم إنه بيفتح استثناء في قاعدة "السيرفر دايمًا المصدر الوحيد للسعر" — الاستثناء محصور في الزنك/التراج بس، مش في أي رقم تاني.
- **خدمات إضافية يدوية (owner, 2026-08-10)**: تكيس، لاصق بنطة واحدة، لاصق 2 بنطة، نموذج — مفيش أسعار ثابتة لها في أي ملف مرجعي، فبقت 4 حقول مبلغ يدوي اختيارية لكل بند (زي `riza`/`jarab` بالظبط في §3.7)، بتتجمع في الـ`subtotal` قبل الضريبة والربح، لأي نوع بند (حتى اللي مالهوش زنك/تراج زي اللوحات والمنتجات الجاهزة).
- **الخصم%** (اختياري، صفر افتراضي): يُطبَّق على مجموع كل البنود (`grandTotal`) قبل الضريبة.
- **ضريبة القيمة المضافة**: **مفتاح تشغيل/إيقاف (Toggle)** وليس خانة رقم - لما يكون شغّال، النسبة ثابتة **14%** تُحسب على (الإجمالي بعد الخصم).
  ```
  afterDiscount = grandTotal * (1 - discount/100)
  vatAmount = vatOn ? afterDiscount * 0.14 : 0
  finalTotal = afterDiscount + vatAmount
  ```
- **التحصيل - دفعات متعددة**: مصفوفة `payments[]`، كل عنصر `{ method, amount }`، وطريقة الدفع من قائمة ثابتة: **كاش، فودافون كاش، Instapay، حساب بنكي**. يمكن إضافة أكثر من دفعة (مثلاً دفعة كاش + دفعة تحويل بنكي لنفس الفاتورة).
  ```
  paidTotal = مجموع كل amount في payments[]
  remaining = finalTotal - paidTotal
  ```
  لو `remaining > 0` → تحذير واضح: **"لا يُسلَّم الشغل إلا بعد سداد الباقي"**. لو وصل صفر → **"تم السداد بالكامل ✅"**.
- **سعر الوحدة المعروض دائمًا** = `item.total / item.qty` (لأي بند فيه qty) - يُعرض في شاشة الحساب، جدول الفاتورة، وأمر الشغل.
- **الفاتورة مستند منفصل عن أمر الشغل** ولهما نفس رقم الفاتورة، لكن تصميم مختلف تمامًا:
  - الفاتورة: شعار، بيانات العميل، جدول (نوع/موديل/مقاس/كمية/سعر وحدة/إجمالي)، صندوق حساب (إجمالي قبل خصم/خصم/ضريبة/مدفوع) **فوق** جدول البنود، صندوق إجمالي أخضر كبير، صندوق حالة السداد.
  - أمر الشغل: **مستند واحد يجمع كل بنود الفاتورة**، فيه QR Code، وبيانات تشغيلية داخلية لكل بند (المقاس الداخلي للطباعة والترقيم اللي العميل مايشوفهوش، عدد التراجات، نطاق الترقيم، نوع الورق، عدد الألوان، لون الحبر، نوع التجليد/السلوفان، الحالة الحالية للطلب).
- **عرض السعر (Quotation)**: نفس تصميم الفاتورة تقريبًا، **بدون** قسم التحصيل/السداد، مع "صالح حتى" (+7 أيام من التاريخ)، ويمكن توليده **من محتوى السلة الحالية قبل الحفظ كفاتورة نهائية**.
- **حالة الطلب (status)**: قائمة ثابتة بالترتيب:
  `['طلب جديد','التصميم','اعتماد العميل','تجهيز الفورمة/الزنك','الطباعة','التشطيب','مراقبة الجودة','التغليف','التسليم','مكتمل']`

---

## 5) قواعد ثابتة يجب الالتزام بها حرفيًا (لا تجتهد فيها)

1. **التقريب دايمًا لأعلى (Ceiling)** في كل مكان فيه تراجات أو أفرخ - أبدًا لأقرب رقم.
2. **الترقيم دالة مستقلة تمامًا عن الطباعة** - لا تربطهم في نفس الكود، ولا تضاعف تراجات الترقيم إطلاقًا مهما كانت الكمية.
3. **المقاس الداخلي (calc size) يُخفى عن العميل تمامًا** - يظهر فقط في أمر الشغل (شاشة تشغيل داخلية)، أبدًا في الفاتورة.
4. **كل نوع فرخ (عادي/جاير) له سعر مستقل تمامًا** حتى لو نفس اسم الخامة - لا يجوز مشاركة سعر واحد بينهم.
5. **قسم اللوحات والإعلانات مستقل تمامًا** بمحرك حساب مختلف (بالمتر لا بالفرخ)، ولا يُضاف عليه profitPercent.
6. **نسبة الربح 25% ونسبة الضريبة 14%** أرقام افتراضية قابلة للتعديل من الإعدادات، لكن يجب أن تبقى قابلة للتعديل من واجهة الإعدادات وليست Hardcoded في الكود بدون مصدر تعديل.
7. **جدول المقاسات (FAMILIES) قابل للتعديل والإضافة من الإعدادات**، لكن أي مقاس مُستخدم فعليًا داخل GROUPS أو NUMBERING_RULES يجب حمايته من الحذف.
8. **كل الحسابات المالية للطلب تُحسب لحظيًا في الواجهة عند إدخال البيانات** (بدون الحاجة لإعادة تحميل الصفحة)، والحفظ للـ Backend يحدث فقط عند "حفظ الفاتورة"/"حفظ وطباعة".

---

## 6) تعليمات التنفيذ لـ Claude Code

1. ابنِ محرك التسعير أولًا كموديول مستقل (Pure Functions فقط، بدون أي اعتماد على واجهة أو قاعدة بيانات) بالضبط زي المعادلات فوق، واكتب Unit Tests للمثال المحلول في القسم 3.5 قبل أي حاجة تانية.
2. اجعل `profitPercent`, `vatRate (14%)`, `notebookThreshold (30)`, `looseThreshold (3000)`, `wasteSheetsDefault (2)`, وكل الأسعار الثابتة (زنك 75، تراج طباعة 75، تراج ترقيم 75، تصميم 75... إلخ) قيم **Settings قابلة للتعديل من قاعدة البيانات**، لا تُثبّتها في الكود.
3. اجعل جدول `FAMILIES` وقوائم أنواع الورق والمنتجات/الخدمات بيانات **قابلة للإضافة والتعديل** من شاشة إعدادات، مع حماية أي قيمة مرتبطة بـ `GROUPS`/`NUMBERING_RULES` من الحذف.
4. صمم الـ Invoice كسجل رئيسي + بنود (Items) كعلاقة One-to-Many حقيقية في قاعدة البيانات (وليس JSON مدمج، لو كنت تبني قاعدة بيانات علائقية من الصفر).
5. اربط الفاتورة بحركة خزينة تلقائية عند التحصيل (نقطة كانت ناقصة في النظام السابق - أضفها هنا من البداية).
6. أضف رقم فاتورة تسلسلي حقيقي (Invoice Number متتابع)، وليس معرّف عشوائي.
7. اجعل "عرض السعر" كيان منفصل قابل للحفظ فعليًا في قاعدة البيانات، مع إمكانية **تحويله لفاتورة** بضغطة واحدة (نقطة كانت ناقصة سابقًا).
